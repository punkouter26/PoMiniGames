1. Auth engine switch

Three named schemes plus the policy scheme that selects among them. AuthSchemes.Composite is the default for both authenticate and challenge; it forwards per request.

SchemeWhere it's registeredWhen it forwards to itselfProduction guards
Composite (policy) Infrastructure/AuthExtensions.cs always — it's the default none (a policy scheme is not a handler)
JwtBearerDefaults.AuthenticationScheme same file, .AddJwtBearer(...) when Authorization: Bearer ... OR ?access_token=... query is present Prod requires MicrosoftAuth:ClientId + MicrosoftAuth:ApiClientId; StartupSecretValidator throws otherwise
DevCookie .AddCookie(AuthSchemes.DevCookie, ...) Dev/Test fallback when no Bearer header is present Prod can register the cookie (the policy is what stops forwarding to it in Prod), but SignInDevelopmentUserAsync returns 404 in non-Dev/Test. So a forged DevCookie cannot authenticate a Prod request — it gets NoResult() and the request ends up anonymous.
FakeAuth .AddScheme<...>(FakeAuthHandler.SchemeName, ...) Dev/Test + Auth:EnableFakeAuth=true + X-Fake-User header present StartupSecretValidator throws if the scheme is registered in Prod. FakeAuthHandler.IsSafeIdentity rejects tampered values (>64 chars, anything outside [A-Za-z0-9._@-]) with a warning and NoResult().

Production guards are triple-locked: (a) the cookie's SignIn short-circuits to 404 outside Dev/Test; (b) the FakeAuth scheme throws if registered in Prod; (c) Auth:AutoGuestLogin throws if true in Prod.

2. BFF handshake & the 401-not-302 rule

2.1 Single-RTT handshake

The legacy flow fetched /api/auth/config and /api/auth/me in sequence — two round trips plus a frame of layout shift. GET /api/auth/handshake collapses both into one response: { config, profile }. AuthStateService.InitializeAsync deduplicates concurrent calls with a SemaphoreSlim + an in-flight Task<?>; the browser-abort race is treated as "keep the previous identity", not "blank the header".

2.2 X-Reauth: 1

If a PoMiniGames.DevAuth cookie was sent but the cookie auth handler produced an anonymous principal (because the data-protection key ring was rebuilt — Azurite wipe, dev-box restart), the handshake endpoint sets X-Reauth: 1 in its response. The SPA detects it on the next page mount, calls /api/auth/dev-logout, and re-issues a fresh guest identity so the user is not stranded on a stale name.

2.3 401-not-302 for /api/*

The cookie auth events deliberately short-circuit the default redirect behaviour:

options.Events.OnRedirectToLogin      = ctx => { ctx.Response.StatusCode = 401; return Task.CompletedTask; };
options.Events.OnRedirectToAccessDenied = ctx => { ctx.Response.StatusCode = 403; return Task.CompletedTask; };

If this is missing, an unauthenticated call to /api/* would be answered with a 302 Found to /Account/Login. The browser would follow the redirect, the SPA shell would render a login page over a JSON consumer, and the client would parse HTML as data — corrupting state. The override is the single load-bearing line that makes the BFF pattern work for a JSON consumer.

3. WASM boot mask

Before BffAuthenticationStateProvider.GetAuthenticationStateAsync resolves a real session, every render assumes anonymous. This is the conservative choice for <AuthorizeView> / <AuthorizeRouteView> gates in App.razor: IsAuthenticated is always false on the first paint, so protected pages route to the login wall without flashing their protected content.

The same provider is an adapter over the BFF's /auth/me HTTP endpoint — it does not hold the bearer token. AuthStateService holds the bearer token (WASM memory) and ApiService attaches it as Authorization on outbound calls. The README's "BFF cookie" line is honest about this: a true token-never-leaves-the-server BFF is a future hardening goal, not the current shape.

4. Auth state machine

Edges follow the order in ForwardDefaultSelector in Infrastructure/AuthExtensions.cs: Bearer header first, then ?access_token= (SignalR hubs), then X-Fake-User (Dev/Test + flag), then DevCookie fallback. The orange edge is the "Dev/Test + FakeAuth enabled" path; the dashed red edge is the cookie-present-but-unprotectable path that triggers X-Reauth: 1.

5. Open-redirect protection

Every returnUrl query parameter is passed through AuthEndpoints.ResolveLocalReturnUrl, which:

  • Requires the value to start with / (rooted relative).
  • Rejects protocol-relative targets like //evil.example or /\evil.
  • Rejects well-formed absolute URLs.

Anything else collapses to /. This is the same defense used by the legacy unprefixed routes (/auth/login/microsoft, /auth/login/fake, /auth/logout).
