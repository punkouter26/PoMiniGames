Audit of the runtime diagnostics the app actually emits, and the gap where interactiveMs / CLS / WASM memory would go. Per the prompt contract, no synthetic numbers are plotted when the data isn't there.

1. Three separate charts (never a dual y-axis)

1.1 Time-to-interactive vs document load

The two lines are plotted on the same axis for comparison, but the chart would highlight that load is not the right signal for Blazor WASM: the document load event fires after the bare HTML is parsed, before the WASM payload finishes downloading, compiling, and rendering the root component. Until interactiveMs is defined and measured, this chart stays empty.

1.2 Cumulative Layout Shift (CLS)

A PerformanceObserver for layout-shift entries is the standard mechanism; the project doesn't subscribe to one. A "good" CLS for web vitals is < 0.1; "needs improvement" is 0.1–0.25. Without samples, the chart is empty.

1.3 WASM heap memory

performance.memory is Chromium-only; even where it exists, sampling at 250 ms intervals during a representative route navigation would surface large retained buffers (e.g. PoMarbleRace scene data). No such sampler exists today.

2. Source toggle

Per the prompt, the source toggle defaults to live data when samples exist and falls back to clearly-labelled synthetic values when they don't. This build renders no synthetic numbers; the empty charts above are the honest fallback. Once DOCS/diagnostic_history.json exists with samples, the toggle becomes meaningful and a switch in the top-right (synthetic / live) is straightforward to add.

4. What collect-vitals.mjs would need to add

The diagnostic pipeline is the only piece of this report suite that is missing entirely. Adding it is straightforward but invasive enough that we don't want to fabricate numbers in the meantime.

  1. Time-to-interactive: Playwright page.evaluate(() => performance.now()) around a sentinel DOM marker the SPA renders after first Blazor render. The load event is the wrong target — it fires after the HTML is parsed but before the WASM runtime has finished.
  2. CLS: new PerformanceObserver(list => list.getEntries().forEach(e => samples.push(e.value))) for layout-shift, scoped to the route navigation.
  3. WASM memory: Chromium-only performance.memory.usedJSHeapSize, sampled every 250 ms across a representative navigation. Discard if undefined.
  4. Sample count: per the prompt, --runs 8 minimum per route. The script should be idempotent (append-only, install deps on first run, start/stop Azurite + host only if they aren't already up).
  5. Output: DOCS/diagnostic_history.json with shape { runs: [{ route, interactiveMs, cls, memorySeries: [...] }] }. The build's @HISTORY marker will pick it up automatically.

5. @HISTORY token resolution

The build script inlines DOCS/diagnostic_history.json as a <script type="application/json" id="diagnostic-history"> element. If the file is absent, the marker resolves to a labelled gap object:

{
  "_gap": true,
  "reason": "diagnostic_history.json not found. Run scripts/collect-vitals.mjs to populate; in the meantime, no synthetic numbers are fabricated.",
  "samples": [],
  "collectedAtUtc": null
}

The chart renderers check data._gap and bail out with a "no samples" badge rather than plotting zero. The charts above render against this exact payload right now.
