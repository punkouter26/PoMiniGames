2. Shape vs the pyramid

A balanced pyramid would be widest at Unit, narrowing through Integration and API, with a small UI apex. Today:

Unit         100  ████████████████████████████ (ceiling = 100)
Integration   49  ██████████████              (ceiling = 50)
E2EAPI        11  ███                         (ceiling = 25)
E2EUI         10  ███                         (ceiling = 25)

This is a pyramid — but with caveats:

  • The Unit tier is pinned to its structural ceiling. Any new test must consolidate an existing one or move to Integration. The ceiling was raised from a default; it is not a recommendation.
  • Integration at 49/50 is healthy headroom. New behavior tests should land here first per CLAUDE.md.
  • E2EAPI and E2EUI both have ~50% headroom under their ceilings. The small number reflects the test budget guard (10 E2E tests can already cover a full Playwright deployment smoke), not under-coverage.

Finding · Unit tier is at the ceiling

100 product test methods (excluding the TestCountCeilingTests guard itself, which the guard's own logic excludes via Where(t => t != typeof(TestCountCeilingTests))). The next test added will trip the guard unless the author consolidates or moves it to Integration. This is exactly the pressure the 100/50/25/25 rule was designed to apply, and it is doing its job.

4. Test budget guard

tests/Shared/TestBudgetGuard.cs is the structural enforcement for the E2E tiers: even with a live Azure OpenAI client wired, the suite refuses to make a real call unless an explicit override is set. The intent is that an accidental key in appsettings.Development.json cannot rack up billing during local test runs.
